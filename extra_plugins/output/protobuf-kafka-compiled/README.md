# PROTOBUF-KAFKA-COMPILED
## Description
PROTOBUF-KAFKA-COMPILED plugin is a modified version of the protobuf-kafka plugin, where the protobuf schema is linked to the program during compilation, which eliminates the delay caused by parsing the schema during program execution. Plugin serializes IPFIX flow records into Protocol Buffers and sends them to a Kafka topic. It features:
- Protobuf schema usage: Before compiling the program, the programmer must generate a C++ version of the schema using the command "protoc --cpp_out=. schema" within the generated_schema folder under the names schema.pb.cc and schema.pb.h.
- RSS Partitioning: flowId-based partitioning (with 5-tuple fallback) for receiver-side scaling. FlowId can be precomputed in IPFIX message in element FLOW_ID. If FLOW_ID is set, this value will be used for partitioning instead of computing new value

## Content
PROTOBUF-KAFKA-COMPILED plugin is divided into following folders:
- CMakeModules: Contains cmake files for finding required libraries.
- generated_schema: Contains raw schema file (schema) and then converted schema to C++ class included in files schema.pb.cc and schema.pb.h. This conversion (schema -> schema.pb.cc + schema.pb.h) is provided by command "protoc --cpp_out=. schema".
- src: Contains following source codes (files with definitions and decrarations) of this plugin:
    - plugin.cpp: Plugin entry point for IPFIXcol2.
    - Config: Processing the plugin's XML configuration.
    - TranslationTable: Creating mappings between IPFIX elements (PEN, ID) and protobuf fields
    - FlowConverter: It performs the conversion of the IPFIX flow record to a Protobuf message.
    - KafkaProducer: Encapsulates communication with Kafka using librdkafka.
- test: Contains following files, which can be used for testing (see Test):
    - docker-compose.yml: Docker Compose configuration for start a test environment (Kafka broker or Zookeeper). Used to quickly start the Kafka infrastructure locally for plugin testing.
    - schema: A protobuf definition file that specifies the structure of a FlowRecord message. Used to generate C++ and Python classes using protoc
    - schema_pb2.py: Automatically generated Python module (generated by command "protoc --python_out=. schema") from schema file. Used in the kafka-test.py test script to deserialize Protobuf messages from a Kafka topic.
    - kafka-test.py: A simple Kafka consumer in Python, which reads messages from a defined topic, deserializes them using schema_pb2 and writes decoded flow data to output.
    - send_ipfix.py: A test IPFIX exporter written in Python. It generates IPFIX template, several datasets and sends them via UDP to this plugin.
    - test.xml: Sample configuration file for this plugin, which sets up UDP input, enables protobuf-kafka-compiled output and defines mapping between IPFIX and protobuf.
    - test-description.txt: Short description, how to test.
In main directory, CMakeLists.txt is included. Thanks to this file, you can build and install this plugin.

## Configuration
The plugin accepts the following XML configuration (can be changed according to requirements):
```
<ipfixcol2>
  <!-- Input plugins -->
  <inputPlugins>
    <input>
      <name>UDP collector</name>
      <plugin>udp</plugin>
      <params>
        <localPort>4739</localPort>
        <localIPAddress></localIPAddress>
      </params>
    </input>
  </inputPlugins>

  <!-- Output plugins -->
  <outputPlugins>
    <output>
      <name>MyProtoKafka</name>
      <plugin>protobuf-kafka-compiled</plugin>

      <params>
        <brokers>127.0.0.1:9092</brokers>
        <topic>IPFlows</topic>
        <partition>precomputed_rss</partition>
        <batch_size>10000</batch_size>
        <linger_ms>100</linger_ms>
        <compression>lz4</compression>
          <map>
            <field ipfix="sourceIPv4Address" proto="SRC_IP"/>
            <field ipfix="destinationIPv4Address" proto="DST_IP"/>
            <field ipfix="protocolIdentifier" proto="PROTOCOL"/>
            <field ipfix="octetDeltaCount" proto="BYTES"/>
          </map>
      </params>
    </output>
  </outputPlugins>
</ipfixcol2>
```

## Parameters
- brokers: Comma-separated list of Kafka brokers (required) 
- topic: Kafka topic to produce to (required)
- partition: Partition strategy: random (default), rss (flowId, fallback to 5-tuple hash), or precomputed_rss (computed flowId is included in IPFIX element FLOW_ID)
- batch_size: Kafka producer batch.num.messages (default: 10000)
- linger_ms: Kafka producer queue.buffering.max.ms (default: 100)
- compression: Kafka compression codec (default: lz4)
- blocking: Block when producer queue is full (default: false)
- map: Field mappings from IPFIX to Protobuf (at least one required)

## Field mappings
Each ``<field>`` element in ``<map>`` specifies:
- ipfix: IPFIX element specification in format ``scope:name`` (e.g., ``iana:sourceIPv4Address``)
- proto: Protobuf field name in the target message
Supported IPFIX to Protobuf type mappings:
- Integer types (8/16/32/64-bit) → int32/int64/uint32/uint64
- IP addresses → bytes or string
- Strings → string
- Octet arrays → bytes
Example mappings for packet-level basicList fields:
```
<map>
    <field ipfix="e0id291/cesnet:packetLength" proto="PPI_PKT_LENGTHS" />
    <field ipfix="e0id291/cesnet:packetTime" proto="PPI_PKT_TIMES" />
    <field ipfix="e0id291/cesnet:packetDirection" proto="PPI_PKT_DIRECTIONS" />
    <field ipfix="e0id291/cesnet:packetFlag" proto="PPI_PKT_FLAGS" />
</map>
```

## RSS partitioning
When ``partition`` is set to ``rss``, the plugin computes a symmetric
hash from the 5-tuple (source IP, destination IP, source port,
destination port, protocol). This ensures:

- Both directions of a flow go to the same partition
- Load is distributed evenly across partitions
- Consumers can process flows in order per-connection

## Precomputed RSS partitioning
When ``partition`` is set to ``precomputed_rss``, the plugin use as RSS value set in IPFIX FLOW_ID element.

## Example proto file
```
syntax = "proto3";

package ipfix;

option optimize_for = SPEED;

message FlowRecord {
    // === Core fields (1-15 use 1-byte tag - most frequent fields) ===
    bytes SRC_IP = 1;                    // iana:sourceIPv4Address / iana:sourceIPv6Address
    bytes DST_IP = 2;                    // iana:destinationIPv4Address / iana:destinationIPv6Address
    uint32 SRC_PORT = 3;                 // iana:sourceTransportPort
    uint32 DST_PORT = 4;                 // iana:destinationTransportPort
    uint32 PROTOCOL = 5;                 // iana:protocolIdentifier
    fixed64 BYTES = 6;                   // iana:octetDeltaCount
    fixed64 BYTES_REV = 7;               // iana@reverse:octetDeltaCount@reverse
    fixed64 PACKETS = 8;                 // iana:packetDeltaCount
    fixed64 PACKETS_REV = 9;             // iana@reverse:packetDeltaCount@reverse
    fixed64 TIME_FIRST = 10;             // iana:flowStartMicroseconds
    fixed64 TIME_LAST = 11;              // iana:flowEndMicroseconds
    uint32 TCP_FLAGS = 12;               // iana:tcpControlBits
    uint32 TCP_FLAGS_REV = 13;           // iana@reverse:tcpControlBits@reverse
    uint32 TTL = 14;                     // iana:ipTTL
    uint32 TTL_REV = 15;                 // iana@reverse:ipTTL@reverse

    // === Flow metadata (16+) ===
    uint32 FLOW_END_REASON = 16;         // iana:flowEndReason

    // === DNS fields ===
    uint32 DNS_ANSWERS = 20;             // cesnet:DNSAnswers
    uint32 DNS_ID = 21;                  // cesnet:DNSTransactionID
    uint32 DNS_Q_TYPE = 22;              // cesnet:DNSQType
    uint32 DNS_RR_RLENGTH = 23;          // cesnet:DNSRDataLength
    uint32 DNS_DO = 24;                  // cesnet:DNSRDO
    uint32 DNS_RCODE = 25;               // cesnet:DNSRCode
    bytes DNS_Q_NAME = 26;              // cesnet:DNSName

    // === TLS fields ===
    uint32 FME_TLS_SERVER_VERSION = 30;  // flowmon:tlsServerVersion
    string TLS_SNI = 31;                 // cesnet:TLSSNI

    // === HTTP fields ===
    uint32 HTTP_RESPONSE_STATUS_CODE = 40;  // flowmon:httpStatusCode
    string HTTP_REQUEST_AGENT = 41;         // flowmon:httpUserAgent
    string HTTP_REQUEST_HOST = 42;          // flowmon:httpHost
    string HTTP_REQUEST_REFERER = 43;       // flowmon:httpReferer
    string HTTP_REQUEST_URL = 44;           // flowmon:httpUrl
    string HTTP_RESPONSE_CONTENT_TYPE = 45; // flowmon:httpContentType

    uint64 FLOW_ID = 50;
    uint64 FLOW_COUNT = 51;
}
```

## Requirements
- cmake (minimum version 3.12)
- IPFIXcol2 2.3.0
- LibRDKafka 0.9.3
- Protobuf
- XXHASH

## Build & Installation
When preparing a plugin, you need to ensure 3 things:
1. Install all dependencies
2. Make C++ protobuf class via command "protoc --cpp_out=. schema" in folder generated_schema
3. Check if the method "void FlowConverter::setField(ipfix::FlowRecord& msg, const FieldEntry& entry, const uint8_t* data, size_t size)" in file src/FlowConverter.cpp contains all types of elements defined in schema. If not, you need to add them according to code above.
4. If package or message name differs from Example proto file, you need to replace all occurences (ipfix::FlowRecord) to correct version
5. Build and install plugin (see Build and instalation):
```
cd extra_plugins/output/protobuf-kafka-compiled
mkdir build
cd build
cmake ..
make
sudo make install
```

## Run
To run plugin you need to type "ipfixcol2 -c filename.xml", where filename.xml contains XML with configuration (see Configuration). Optionally you can use option -v, -vv, or -vvv for printing additional information during run.

## IPFIX and Kafka Interconnection
This plugin should receive IPFIX messages in input and it sends protobuf messages to Kafka.

## Test
In folder test:
1. Generate C++ schema (protoc --cpp_out=. schema) in folder "generated_schema" and python schema (protoc --python_out=. schema
) in folder test.
2. Build and install plugin (see Build & Installation).
3. Start plugin (ipfixcol2 -c test.xml -vvv)
4. Start kafka:
sudo docker-compose up -d
python3 kafka-test.py
5. Send test IPFIX
python3 send_ipfix.py
Sent bytes should be seen in kafka-test.py
